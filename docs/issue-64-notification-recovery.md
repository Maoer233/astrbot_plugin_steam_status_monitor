# Issue #64：通知积压修复方案

## 问题与目标

QQ 离线或持续发送失败时，旧通知整批回队并与新通知合并，恢复后单条消息可能包含数百张图片。现有轮询等待期间也会频繁 flush，进一步放大重试与渲染负担。

目标：通知有界、过期淘汰、故障会话退避、小批次恢复、成功批次不重发。通知丢弃不得影响游玩时长、持久化或排行榜。

## 范围

沿用现有队列、事件去重键和 `_target_session`，不新增调度服务、依赖、在线状态探测、图片缓存或消息降级。不修改游戏会话状态机。保留静默不补发，以及游戏库独立持久化重试语义。

## 节点与提交

1. **方案文档**：记录范围、默认策略和验收标准，单独提交。
2. **分批与结果结算**：每个目标串行发送，每批最多 5 条通知；先选批再渲染；成功批次不回队，失败后停止该目标剩余批次；逐条区分无内容、渲染失败和发送成功；异常/取消释放 inflight，恢复未完成而非成功项。完成专项回归后提交。
3. **有界队列与会话退避**：统一生产入队与回队路径；首次入队时间不随重试重置；30 分钟 TTL、每目标最多 100 条、全局最多 1000 条，先清过期再淘汰最旧项；目标失败后按 30、60、120、240、300 秒封顶退避，成功重置；冷却期间新通知也不发送或渲染。完成回归后提交。

以上为内部保护默认值，不代表平台限制。TTL 已限制通知寿命，不再叠加逐条重试次数。容量包含 flush 期间未完成的记录，目标路由展开后计数；同事件按目标独立结算。静默时段待发项仍直接消费。游戏库调用共享发送接口时，不得把暂缓错误地返回为成功，也不重复接管其持久化队列。

## 验收

- 243 条通知按最多 5 条分批，失败后剩余批次不继续发送。
- 第一批成功、第二批失败：第一批不重发，失败和未发送项保留。
- A 目标成功、B 失败：只保留 B；正常目标不受 B 的退避影响。
- 仅图片模式部分渲染失败：失败项不随其他成功图片一起确认。
- 高频 flush 与故障期间新事件：冷却内没有发送和渲染调用。
- 持续入队：目标及全局上限有效，超限优先淘汰旧项；过期项不补发。
- 取消/异常：inflight 释放、当前及尚未处理群的通知不意外丢失。
- 回归静默、上线/下线、开始/结束、去重及游戏库通知。

## 限制

发送接口超时仍可能实际送达，现有平台契约无法保证恰好一次。通知队列继续只存内存，不跨重启补发。临时图片完整生命周期治理另行处理，不与本修复捆绑。
